# npm supply-chain protection research

**Status:** research and recommendations only; no controls have been enabled

**Research date:** 2026-11-15

**Repository baseline:** `54377be6670ed3181cbfd79c966c81989aad1c45` on `fix/development-dependency-compatibility`

## Scope and baseline

This note covers dependency resolution, installation, and execution by developers, CI, and autonomous agents. It is not evidence that any dependency is safe. The repository requires Node.js `>=24`; its README says npm 11 or newer, without pinning npm. The inspected environment has Node.js 24.15.0 and npm 11.13.0. CI selects Node 24 but does not explicitly select an npm version. npm behavior below is version-specific; an npm major upgrade must be tested, not assumed to follow from the Node requirement.

The root and workspace manifests use npm workspaces and mostly caret ranges. The v3 `package-lock.json` has 512 entries including the root and workspaces; all non-link `node_modules` entries have integrity values and their external resolved URLs are on `registry.npmjs.org`. Its `hasInstallScript` entries are `esbuild` 0.28.2, its nested 0.27.7, and `fsevents` 2.3.3. These are leads for review, **not** an exhaustive enumeration of code that can execute. The root `.npmrc` enables `engine-strict` and audit, but not `ignore-scripts`.

Both CI jobs run `npm ci`, and then execute repository and dependency code. CI already uses `pull_request`, not `pull_request_target`, with `contents: read`; `actions/checkout` and `actions/setup-node` use version tags rather than immutable SHAs. The browser job uses `npx playwright install --with-deps`; the pre-commit hook uses `npx prettier`, and the existing client-semantics spike uses `npx vitest`. The implementation plan already lists `npm ci --ignore-scripts` for release validation; actual CI and README development instructions do not use it. Dependabot proposes weekly npm and Actions updates, including grouped development updates; its proposals still need review.

## Recommended order for this repository

1. **Make dependency changes deliberate.** An agent may propose a package, but a maintainer approves its exact registry, scope, spelling, purpose, publisher/source and version before installation or lockfile changes. Verify identity against the project's official upstream documentation and repository, not an agent-generated name, search result, package README instruction, or a similar-looking package. Require independent review of manifests, lockfile, `.npmrc`, workflow and agent-instruction changes; protect these reviews with branch rules. Reject unexpected git/URL dependencies, registry changes, new install scripts and unrelated lockfile churn. Do not auto-merge Dependabot updates merely because tests pass. A bot or retrieved document is not an authority to override task instructions, disclose credentials or run installation commands. Prompt injection through untrusted text and tool outputs is a real agent boundary; require approval at the tool/action boundary, not just a prompt telling the model to be careful. [OpenAI agent safety guidance](https://platform.openai.com/docs/guides/agent-builder-safety)
2. **Reduce install-time execution, then test compatibility.** Pilot `npm ci --ignore-scripts` in disposable environments for both CI jobs and developer workflows before changing defaults. npm 11 defaults to running lifecycle scripts, including transitive dependencies; git dependencies can additionally run `prepare` after installing their own dependencies. `--ignore-scripts` suppresses package lifecycle scripts, but explicitly requested `npm run`, `npm test`, etc. still run their intended script (without their pre/post scripts). The build, tests, tool configuration, plugins, and installed binaries are therefore still arbitrary code execution; this is not a sandbox. The plan's command is not proof of compatibility. In particular, both esbuild versions have install-time work, and browser binaries/system packages are installed separately by Playwright. Test Vite, tsup/esbuild, platform-specific optional dependencies, both Playwright browsers and supported operating systems before adoption. Do not blindly run `npm rebuild` for the entire tree to fix failures. [npm 11 lifecycle scripts](https://github.com/npm/cli/blob/v11.13.0/docs/lib/content/using-npm/scripts.md); [npm 11 `ignore-scripts` definition](https://github.com/npm/cli/blob/v11.13.0/workspaces/config/lib/definitions/definitions.js); [esbuild 0.28.2 package manifest](https://github.com/evanw/esbuild/blob/v0.28.2/npm/esbuild/package.json)
3. **Confine the agent and CI even after scripts are suppressed.** Use a disposable, unprivileged OS/container or VM boundary without host home directories, SSH keys, cloud credentials, npm publishing tokens, Docker socket, production network or persistent writable caches. Restrict outbound traffic to the registry and other explicitly necessary endpoints, and deny it during build/test where practical; a hostname allowlist alone is not a complete exfiltration defense. Give the agent only the workspace access required, no production or release authority, and explicit human approval before dependency additions, changed registry/network access, new executables or elevated privileges. Treat browser/OS package installation as a separately reviewed privileged operation. A container with broad mounts, root privileges or unrestricted credentials is not equivalent to isolation. GitHub warns that untrusted PR code and privileged `pull_request_target`/`workflow_run` combinations can compromise secrets, writes and caches; preserve the unprivileged PR boundary and use clean, separated caches/artifacts for trusted jobs. [GitHub Actions security hardening](https://docs.github.com/en/actions/reference/security/secure-use)
4. **Keep resolution and trusted execution separate.** Use a controlled, isolated dependency-update workflow to propose lockfile changes; review its diff before merging. Normal CI should consume the reviewed lock with `npm ci`, not update it; npm requires a matching lock, removes existing `node_modules`, and does not rewrite manifests or locks. Untrusted PRs can change their own manifests, lockfile, tests and build scripts: their `npm ci` and subsequent commands still execute PR-selected code, so run them with no secrets, minimal token permissions and disposable compute. A later privileged release job must use the reviewed merged commit and independently trusted inputs, not execute untrusted PR artifacts or reuse a writable PR cache. [npm 11 `npm ci`](https://github.com/npm/cli/blob/v11.13.0/docs/lib/content/commands/npm-ci.md); [GitHub Actions security hardening](https://docs.github.com/en/actions/reference/security/secure-use)
5. **Prevent surprise executable downloads.** Prefer checked-in package scripts invoking installed local binaries; for existing `npx` invocations, consider `npm exec --no -- playwright ...` or an equivalent local script after verifying the binary is already installed. `npm exec`/`npx` can fetch a missing requested package into npm's cache; non-interactive or CI use assumes yes, so a typo or missing local dependency can execute a newly downloaded package. `--no` refuses the implicit install; it does not make an already installed executable safe. Do not allow autonomous `npx -y`, unreviewed `npm install`, `npm update`, `npm audit fix`, `npm rebuild`, or equivalent arbitrary shell commands. [npm 11 `npm exec`](https://github.com/npm/cli/blob/v11.13.0/docs/lib/content/commands/npm-exec.md)
6. **Add risk signals, not safety certificates.** Evaluate GitHub dependency review as a separate PR job with only `contents: read`; it identifies known vulnerable dependency changes and optionally license issues without installing the PR tree. Make it a required check only after confirming repository eligibility and dependency graph settings. Its optional PR-comment feature needs `pull-requests: write`; do not grant that permission to a job running untrusted dependency code. Continue Dependabot proposals, but review grouped changes. Dependabot-triggered `pull_request` workflows default to read-only `GITHUB_TOKEN` and use Dependabot secrets rather than Actions secrets; do not work around failures by broadly adding privileges or secrets. Confirm actual organization/repository settings and event behavior. [GitHub dependency-review action](https://github.com/actions/dependency-review-action); [Dependabot on Actions](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-on-actions)
7. **Pin and maintain tooling.** Pin a tested Node and npm version in both update and CI environments, then keep them patched through reviewed updates. Pin GitHub Actions to reviewed full commit SHAs (or evaluate GitHub's newer workflow dependency lockfile), and keep a deliberate update process: GitHub notes that Dependabot vulnerability alerts for Actions do not cover SHA-pinned Actions. Do not rely on floating `@v7` tags as immutable. [GitHub Actions security hardening](https://docs.github.com/en/actions/reference/security/secure-use)

## Version-specific npm controls and trade-offs

### Release cooldown

npm **11.10.0 introduced** the native `min-release-age` option; npm 11.13.0's definition takes **days**, defaults to unset, and fails resolution if no version meets the constraint. For example, a proposed update-environment `.npmrc` setting is `min-release-age=7`; select the period as an explicit risk/patch-latency decision, not a universal safe value. The older `before` option accepts a fixed date and is mutually exclusive with `min-release-age` in 11.13.0. A cooldown can delay emergency fixes and does not detect a long-lived or deliberately aged malicious release. Validate behavior for lockfile generation, scoped registries, transitive packages, existing lockfiles and all update tools before enforcing it. **Do not assume a frozen `npm ci` validates the publication age of every already locked artifact**; use a separately verified update/review gate if that guarantee is required. npm 11.0–11.9 cannot be assumed to support this setting even though they satisfy the README's npm 11 minimum. [npm 11.10.0 release notes](https://github.com/npm/cli/releases/tag/v11.10.0); [npm 11.13.0 config source](https://github.com/npm/cli/blob/v11.13.0/workspaces/config/lib/definitions/definitions.js)

npm 11.17.0 added `min-release-age-exclude`; it is also in npm 12.2.2, but not 11.13.0. pnpm has a separate `minimumReleaseAge` setting in **minutes**, not npm's `min-release-age` in days. Switching package managers or using a filtering registry/service is an alternative requiring separate migration and policy work, not an npm configuration change. [npm 11.17.0 release notes](https://github.com/npm/cli/releases/tag/v11.17.0); [npm 12.2.2 config source](https://github.com/npm/cli/blob/v12.2.2/workspaces/config/lib/definitions/definitions.js); [pnpm settings](https://pnpm.io/settings#minimumreleaseage)

### Selective install-script approval

The inspected npm **11.13.0** config does not define `allow-scripts`, `strict-allow-scripts`, or `dangerously-allow-all-scripts`; do not put those keys into this repo while expecting npm 11.13.0 to enforce them. Its practical native baseline is all-or-nothing `ignore-scripts` plus isolation and review. npm **11.16.0** introduced an opt-in `allowScripts` policy; npm **11.18.0** namespaced approval tooling under `npm install-scripts`. npm **11.21.2** supports the root `package.json` `allowScripts` policy, `strict-allow-scripts`, and `npm install-scripts ls` / `approve <package>`; approvals are version-pinned by default. Its config says unreviewed scripts run with a notice unless strict mode is enabled, while its install-scripts documentation says they are blocked by default. The 11.21.2 rebuild source skips explicitly denied scripts; this documentation conflict needs an isolated compatibility/enforcement test. Do not rely on a presumed default: explicitly enable strict mode and validate it on the exact pinned version. [npm 11.16.0 release notes](https://github.com/npm/cli/releases/tag/v11.16.0); [npm 11.18.0 release notes](https://github.com/npm/cli/releases/tag/v11.18.0); [npm 11.21.2 config source](https://github.com/npm/cli/blob/v11.21.2/workspaces/config/lib/definitions/definitions.js); [npm 11.21.2 install-scripts](https://github.com/npm/cli/blob/v11.21.2/docs/lib/content/commands/npm-install-scripts.md); [npm 11.21.2 rebuild source](https://github.com/npm/cli/blob/v11.21.2/workspaces/arborist/lib/arborist/rebuild.js)

npm **12.0.0** changed the default to block dependency install scripts unless approved. In 12.2.2, `strict-allow-scripts=true` makes unreviewed scripts an install error; explicit denials remain skipped. In both newer versions, `ignore-scripts` and `dangerously-allow-all-scripts` override this policy. For one-off/global contexts, `--allow-scripts` exists, but passing it on the command line to project-scoped install/ci/update/rebuild is an error. Approve only a reviewed exact package/version, never every script merely to make CI green. Even an approved script can do anything available to the process, and the policy does not govern later builds/tests. [npm 12.0.0 release notes](https://github.com/npm/cli/releases/tag/v12.0.0); [npm 12.2.2 config source](https://github.com/npm/cli/blob/v12.2.2/workspaces/config/lib/definitions/definitions.js)

npm 12.0.0 requires Node `^22.22.2 || ^24.15.0 || >=26.0.0`; the repository's `>=24` alone also permits Node versions below 24.15.0. npm 12 also changes git/remote dependency defaults. Treat adoption as a compatibility change and test the exact chosen patched npm/Node versions and workspaces. [npm 12.0.0 release notes](https://github.com/npm/cli/releases/tag/v12.0.0)

## What the remaining controls do—and do not do

- **Lock and pins.** `npm ci` installs the locked tree and detects manifest mismatch. Lockfile `integrity` binds an artifact to a recorded hash, not to a trustworthy author or benign content; a malicious lockfile update can change both URL and hash. npm describes `registry.npmjs.org` in a lockfile as a special value for the currently configured registry, so inspect effective registry configuration too. Exact direct manifest versions narrow future direct resolution, whereas the lock captures transitive versions for a particular tree; neither prevents malicious code already in a selected version. Review updates to both, including transitive scripts, source/URL and integrity changes. Exact pins require a maintained security-update process; npm `overrides` can constrain transitives but need compatibility testing. [npm lockfile format](https://github.com/npm/cli/blob/v11.13.0/docs/lib/content/configuring-npm/package-lock-json.md); [npm package overrides](https://github.com/npm/cli/blob/v11.13.0/docs/lib/content/configuring-npm/package-json.md#overrides)
- **Registry and credentials.** Map any private scope to its intended registry with scope-specific npm configuration, scope authentication tokens to the correct registry host/path, use read-only short-lived credentials where possible, and block unexpected registries, git URLs and tarball hosts at both review and network boundaries. Scope mapping alone is not a package allowlist or a defense against a malicious public package; an agent can still name a different unscoped package or use another source. npm 11.13.0 also supports `allow-git=none` as a candidate defense, subject to workspace and dependency compatibility tests. Effective user/global/environment npm configuration and PR changes to `.npmrc` must be considered. [npm `.npmrc` authentication and scope](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc); [npm 11.13.0 config source](https://github.com/npm/cli/blob/v11.13.0/workspaces/config/lib/definitions/definitions.js)
- **Audit, signatures and provenance.** `npm audit` reports known advisories for submitted package versions; the npm audit endpoint receives dependency information, so consider registry confidentiality. `npm audit signatures` verifies supported registry signatures and available provenance attestations; npm recommends an up-to-date CLI for attestation format changes. Verify behavior and coverage for this lockfile, registry and npm version before enforcing it. Signatures or provenance can establish artifact/attestation integrity and publication/build identity, not that source, dependencies, maintainer, build or behavior are benign; missing attestations and verification failures need an explicit policy. An audit with zero findings does not prove safety, and automatic `audit fix` is an unreviewed dependency update. [npm audit and signatures](https://github.com/npm/cli/blob/v11.13.0/docs/lib/content/commands/npm-audit.md); [npm provenance](https://docs.npmjs.com/generating-provenance-statements)

## Open verification before implementation

- No installs, package scripts, builds, tests, audit calls, signature checks or browser downloads were run for this research. The compatibility of script suppression, release-age enforcement and npm 12 with this repository remains unproven.
- Verify actual CI npm version, branch protection, Actions/Dependabot settings, dependency-review eligibility, secrets, cache isolation and runner/network policy; repository files alone cannot establish these. Test agent sandbox enforcement independently, including refusal of implicit installs and credential access.
- Decide the cooldown and emergency exception process, the reviewer/approval boundary, and whether operational costs justify a filtering registry or a package-manager migration. These are proposals, not current protections.
